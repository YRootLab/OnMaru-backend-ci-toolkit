# 상세 기술 보고서 프롬프트

CI/CD, 테스트, 성능, 장애, 아키텍처 변경처럼 수치와 근거가 중요한 주제를 상세 보고서로 기록할 때 사용한다. 결과물은 `OnMaru/reports`에 저장하며, 읽기 쉬운 포트폴리오 버전은 별도 inbox 프롬프트를 사용한다.

## 입력 템플릿

```text
제목 / 대상 시스템 / 관측 기간:
질문: 이 보고서가 답해야 하는 질문:
변경 전 구조와 관측값:
변경 내용과 적용 시점:
변경 후 구조와 관측값:
실행 링크·artifact·로그 근거:
비교 조건: commit SHA, runner, cache, toolchain, 명령, 설정 hash:
실패·취소·누락·환경 차이:
확정 가능한 결론:
아직 확정할 수 없는 결론:
다음 측정 또는 조치:
```

## 요청 프롬프트

```text
당신은 재현성과 사실성을 우선하는 CI·성능 관측 엔지니어다.
아래 입력으로 한국어 Markdown 상세 기술 보고서를 작성하라.

반드시 다음을 포함하라.
1. 한 문단의 결론: 확정된 사실과 미확정 사실을 분리한다.
2. 측정 범위와 증거 품질: 실행 링크, 표본 수, 비교 가능 여부를 표로 정리한다.
3. 변경 전과 변경 후 구조: 필요할 때만 Mermaid를 사용하며 노드는 7개 이하로 제한한다.
4. 단계·모듈별 시간, 실패율, queue time, critical path 등 실제 수치를 표로 설명한다.
5. 병목과 원인: 관측 사실과 추론을 구분한다.
6. 변경 효과: comparable evidence가 있을 때만 median, p95, delta를 계산한다.
7. 실패·취소·환경 불일치 사례와 왜 성과 판정에서 제외하는지 설명한다.
8. 재현 가능한 다음 측정 계획과 의사결정 기준을 적는다.
9. 원시 로그·secret·consumer source는 본문에 넣지 않고 안전한 링크와 집계값만 쓴다.

사실성 규칙:
- 서로 다른 commit SHA, runner image, cache state, test command, toolchain은 직접 비교하지 않는다.
- failed, cancelled, timeout, artifact 누락 표본은 improvement/regression 판정에서 제외한다.
- 표본이 부족하면 `inconclusive` 또는 `측정 중`으로 표시한다.
- CD 성공 표본이 없으면 실패까지 걸린 시간을 배포 성능이라고 부르지 않는다.
- 측정값과 해석, 권고를 서로 다른 문단 또는 표 열로 분리한다.

입력:
{{INPUT_DATA}}
```
