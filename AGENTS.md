# Repository Operating Guide

## Source of truth

- GitHub Issues are the source of truth for triaged, actionable work.
- `project-roadmap.md` contains only long-term vision and milestone goals.
- `handoff.md` contains current-session state; `improvements.md` contains untriaged ideas.
- `docs/prd.md` is the product requirements source; ADRs in `docs/decisions/` record durable architecture decisions.
- Generated reports and ADR indexes must be regenerated by their canonical tooling.

## Work tracking

- Before starting non-trivial work, search for or create a related GitHub Issue with context and acceptance criteria.
- Link the Issue and branch in `handoff.md` before implementation.
- Record ad hoc requests in `handoff.md` when they affect the current session, or in `improvements.md` when they are follow-up ideas.
- Before opening a Pull Request and again before merge, reconcile work logs, Issue state, branch state, and verification results.
- Every PR references its related Issue. Use an auto-close keyword only when the merge should close that Issue.

## Git Flow Branch Policy

- Integration branch: `develop`.
- Production branch: `master`.
- Work branches: `feature/*`, `fix/*`, and `docs/*` merge into `develop`.
- Release branches: `release/*` merge into `master` and back into `develop`.
- Emergency fixes: `hotfix/*` merge into `master` and back into `develop`.
- Direct pushes to `develop` and `master` are prohibited once branch protection is enabled.
- Required checks are `ci` and repository-specific verification.
- Semantic version tags such as `v0.1.0` are created only from `master` after release verification.
- Short-lived branches are deleted after merge.

## Release policy

- Release mode: release PR generated by Release Please.
- Release source: a successful release merge to `master`.
- Changelog entries are reverse chronological in `changelog.md`.
- Generated artifacts are rebuilt and verified before a tag or GitHub Release is created.
- Release workflows use least-privilege permissions, concurrency control, and `[skip ci]` for generated release commits.
- A failed verification prevents tagging and publishing.

## Safety and verification

- Do not commit secrets, credentials, generated raw benchmark data, or consumer source code.
- Treat consumer repositories and fork PRs as untrusted input.
- Run fresh verification before claiming completion.
- Do not change branch protection, close Issues, or delete data without an explicit scoped request.
